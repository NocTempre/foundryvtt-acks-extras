## 2026-11-13 — An empty compendium id list is answered without the server (T-0353)

**Asked.** A timed import's abilities step made 4169 `getDocuments` calls for
729 item writes (importer DECISIONS, 2026-11-13, "An update pass costs a write,
not a library read"). Core makes two of them per compendium update, each asking
`getDocuments({_id__in: ids})` with `ids` empty for a document the pack already
holds (`ClientDatabaseBackend#loadCompendiumDocuments`, which guards no length),
and the server answers every compendium query by testing every stored document.

**Ruled.** `patches/compendium-empty-load.mjs` wraps
`CompendiumCollection#getDocuments` and resolves `[]` when the query's only term
is an empty `_id__in`, with no server call. Every other query, a `getDocument`'s
`{_id}` among them, reaches core unchanged. libWrapper `MIXED` where it is
installed, a plain wrap otherwise, as the token-light patch does. The patch
holds nothing, so it never answers for a deleted document, and every client runs
it, which also removes the scans other clients' writes cause. Lib owns it: the
method is core's and every feature's writes pass through it, so no feature's
folder is the owner; it is the only wrapper of `getDocuments` in the family.

**Rejected.** *Batching the update pass's writes per pack.* It spares one pass,
leaves every other bulk write and every other client paying the scans, and needs
a single-write retry for a chunk holding a document deleted mid-run. It is the
fallback if the patch is refused. *Skipping the call in the importer.* The call
is core's, inside `Document#update`.

**The counter-argument (moderate).** The patch changes Foundry for every caller
in the world, and a later core that gave an empty query a server-side meaning
would be bypassed without a sign. The match is exact (one key, an empty array),
the current server's `get` runs a plain scan that returns nothing for it, and
core can add the guard itself, at which point the patch is deleted.

*Cost:* a core release that changes what an empty `_id__in` returns is not seen
by the one caller shape this answers; the patch's suite pins the match and the
passes-through cases, and the live import count in importer TESTING, "Counting
reads", shows the loads gone.

## 2026-11-13 — A gate names a capability, and two providers of one do not stack

**Ruled.** A capability is what an ability lets you do, named independently of which ability grants it. Abilities declare what they `provide`; prerequisites, gates and stacking rules are written against the capability, not against one entry. The books print the same capability several ways (a skill, a proficiency, a class power, an alias under another name), and a gate written against one exact definition id misses the rest, where a `kw:` gate catches them all because each provides the capability. It also gives aliases and non-stacking one mechanism instead of two: two abilities that provide the same capability are the same capability twice, so they do not stack, and that falls out of the data rather than being asserted per pair.

## 2026-11-13 — A target-alignment scope is a gate or a sign flip, and they are different rules

**Ruled.** The books write two target-alignment scopes and they are not the same rule. A `gate` applies the bonus versus the named alignment and does nothing otherwise. A `sign` flips to a penalty of the same size versus everyone else.
**Rejected.** Storing either as the other, which is wrong by up to double the value in the direction that matters most.

## 2026-11-13 — A wear slot is an exclusion counted against magic items

**Ruled.** A slot is an exclusion, not a bonus: an item's form is mechanically irrelevant except that a character may not wear two magic items of the same form at once. `capacity` is therefore the magic capacity of the place, what `item-model.mjs` `slotUse` counts magic items against; what the body can physically carry twice is a second count there, where armour and weapons take a place and clothing and plain gear take none. `capacity: null` is unlimited, and the belt and the back are uncapped because several different forms hang from each. A slot assignment that is slightly wrong costs only mis-scoped exclusivity, which is why gear may declare its slot as a correctable guess.

## 2026-11-14 — The command capacity is read off the page, all three rungs

**New evidence.** The archived 2026-09-22 entry "The squad command-capacity figure is an interpretation, not a printed number" (in `DECISIONS-through-v11.14.5.md`) held the first-level rung to be unprinted. RR p. 169, the Mercenaries section's bullet on personal leadership, prints three rungs, each a minimum leader level and a count for infantry and a count for cavalry, the first level's among them. The mounted count is not half the infantry count at every rung. That entry is superseded, and it has no row under "In force" to change.

**Ruled.** The module holds no level and no count of that ladder. A `proseValues` recipe, `wages.commandCapacity`, reads the nine figures from the Judge's own copy (`importer/table-recipes.mjs`); `henchmen/rules/wages.mjs` `commandRungs` turns them into rungs; `group-logic.mjs` `platoonCapacity(level, rungs)` answers the highest rung whose minimum the officer meets. Three states stay apart and each shows differently:

- Nothing imported, or any rung unreadable: no status and no warning at all, and no "not imported" text. The table is taken whole or not at all, because a ladder with a rung missing would rank an officer below every rung they in fact hold.
- An officer under the lowest rung: over-command, as the 0th-level case was, with a message that names no limit.
- A rung in force: the unit is compared with it, and the warning names the rung's two counts.

**The session's call, owner may overrule: a unit of both arms.** The page states nothing for a mixed unit. Infantry and cavalry are each held to their own count of the rung in force, and a unit with both is over when the infantry's share of its count plus the cavalry's share of its own passes one, which reproduces the page exactly for a pure unit. `troopStrength`'s doubling of mounted bodies is gone, since the page's cavalry count is not half the infantry's. A reversal (a mixed unit over only where either arm alone is, or where a Judge's own rule of conversion applies) changes `group-logic.mjs` `commandStatus` and its two suites, and nothing imported.

**Rejected.** Keeping the first rung as an interpretation beside the two printed ones; converting cavalry to infantry-equivalents at a fixed ratio, which the page's own counts contradict.

*Cost:* the group's `troopStrength`, `commandCapacity` and `overCommand` getters are removed for `troopCounts` and `commandStatus(rungs)`, so lib `apiVersion` is 45. A world that has not imported the Rules tables hires an over-large unit with no warning.

## 2026-11-18 — A place carries its things, one list in one shape for every feature

Co-signed by scene-search and obstacle regions. The
owner's words that set it, 2026-11-18: on obstacles, "Conditions are present
when added, most easily by dragging. This is akin to a natural trap. Not doing
a big switchboard of possibilities.", "Traps, obstacles, conditions can stack
arbitrarily." and "This is some variation of location."; on scene search, "This
is becoming a whole scene tool and could incorporate things like inspecting
statues/art", and "No picked clean state, only checked hastily and checked
methodically for each inspectable".

**Ruled.** The carrier is the place, the `acks-extras.location` actor. What
the Judge drags onto a place is a THING, kept in one list at
`flags["acks-extras"].things`, written whole by a GM client as a
`ForcedReplacement`. Any number of things of any kind stack on one place, and a
nested place carries its own. The list is called "things", never "stack":
`place.mjs` already means identical places by "stack" (`isStacked`). Every
thing has one shape:

```
{id, kind, ref, hidden, hint, point, params, layers: {hasty?, methodical?}, state}
```

- `kind` — one of `body`, `container`, `fixture`, `exit`, `trap`, `obstacle`,
  `condition`, `lot`, `floor`. A feature registers the kinds it accepts in
  one `kindOfDrop` table (`place-things-logic.mjs`); there is no second table.
- `ref` — the uuid of the document the thing stands for: a trap Item, a Hazard
  (an `acks-extras.hazard` Item, an obstacle or a condition, keyed by its
  `system.key`), stored goods, a JournalEntryPage, an Actor. The thing points
  and never copies.
- `hidden` — authored: the thing starts unseen by players.
- `hint` — the Judge's optional line the table sees when something more
  remains, or null for the generic words.
- `point` — `{x, y}` in scene pixels where a map drop put it, null for a
  sheet drop. Reach is measured from it.
- `params` — the kind's own authored figures, owned by the kind's registrant
  (an obstacle's `length`, `gap` and `depth`, each nullable, blank meaning the
  Judge sets it at the table; a condition's is empty).
- `layers` — authored per check: `hasty` (a round) and `methodical` (a turn),
  each optional. Scene search owns their keys.
- `state` — runtime progress only, and the only part a Reset clears. Its keys
  belong to the kind's registrant (a trap's `known`, `searchLock`,
  `repeatLock`, armed state) and to scene search (`state.layers`, what each
  check found and who failed it); a thing shown to players by a check carries
  it here, so a Reset hides it again.

**Owners.** lib: the shape, `normalizeThings`, the writes. location: the drop
branches on the sheet, the token and the area's Region, `placesAround`, and the
sheet's Things here list. formation (close-out): trap and obstacle semantics,
area triggers and doors, and trap-zone's third `Placement` source, which reads
a trap thing and keeps no copy. scene-search: layers, activities, the screen
and the session. treasure: the pot.

**Derived, never stored:** doors (core walls touching the place's area, where
`door === 2` is a hidden exit), trap zones and trap walls placed on the map in
the area (hidden unless `known`), and a fight's bodies (read from Search the fallen's
record). Goods dropped on a place still go to its goods, as today.

*Rejected:* an embedded copy of the trap or Hazard (two sources of truth, and a
book's text copied into a world flag); a list per feature (two writers of one
place, and the owner's stacking across kinds needs one list); a per-kind
switchboard of authored options (the owner's "Not doing a big switchboard").
*Counter (medium):* one flag written whole means two GMs editing one place's
things at once lose the earlier write; the write is GM-only, frequent `state`
writes come from one client, the primary GM's, and the other branch, a
document per thing, costs a document type for what is a row.

**Where the list lives.** The owner, 2026-11-18: "Everything to a place that
can apply effects to a region. All to region if easiest". The list stays on the
place, which applies its things over its linked Region. Keeping it on the Region
instead would leave imported keyed rooms empty, since they are laid as place
tokens with no Region, and it would need a second carrier. All it would save is
one `locationOfRegion` lookup at entry and a redraw hook.

*Cost:* a thing whose `ref` was deleted stays until the Judge removes it, and
reads as a missing document rather than vanishing; nothing migrates, since no
earlier shape shipped.

## 2026-11-24 — A join outside the holder's turn is refused, and a sheet's drop joins in turn

**Ruled.** `joinStacks` re-reads both rows on the holder (`holder.items.get(id)`)
before its first write and does nothing when either is gone. `joinInTurn(item,
onto)` is the join for a caller outside a turn: it queues on the holder
(`oneAtATime`), looks both rows up again when its turn comes, and calls
`joinStacks` only if both are still there. A task already inside a turn, such as
`foldIntoRest`, calls `joinStacks` directly, since `joinInTurn` waits on the
turn that task is part of. The character sheet's drop onto a row of the same
thing calls `joinInTurn`.

**Why.** Dragging a drawn weapon or worn armour onto its own resting row on the
character sheet unequips it first. That write's `updateItem` hook queues
`foldIntoRest`, which joins the resting row into the drawn one, in turn. The
drop's own join then ran outside the queue, read the counts before the fold's
writes came back, and joined the drawn row into the resting one. Each side
raised one row and deleted the other, so both rows were deleted and the stack
was lost. The existing-row check alone does not close this, since both rows are
still there when the drop's join starts; the queue does.

**Rejected.** Leaving the guard to `joinStacks` alone (it sees only writes that
have landed). Taking the join out of the drop (a stack let go on another row
should join, and the fold only covers a row that was in use).

*Cost:* lib `apiVersion` is 67 (`itemModel` gains `joinInTurn`). A join through
`joinInTurn` waits behind every divide and fold already queued on the holder.

so a charge's disorder rides on the one Charging effect Foundry builds, and the
holder, the second effect, the refusal and the prompt are not built.

This supersedes in part "Core's condition effects carry the figures they
reach" (above), an entry of the same day: its Cost paragraph says two effects
naming one condition both apply and the module deduplicates none of it, leaving
that to the writers. The new evidence is the owner's reply quoted here;
Foundry 14.370's `fromStatusEffect`, which builds one effect for a status
entry that names others, and its `shouldApplyChange`, which a system or a
module may override to refuse a change; and a run on the test world in which
Foundry's implicit statuses alone counted a brought condition twice beside a
hand-set copy and beside a second state that brings it. That entry's "a later
slice" is this one.

**Ruled.**
- A catalogue state whose `implies` names a condition that carries changes in
  the system's list, and whose own closure does not forbid acting, is
  registered as one status entry with `statuses` (the brought conditions that
  carry changes), a static `_id` and its own changes followed by each brought
  entry's, read at registration. The set is derived and never listed in
  source. The `_id` is a pure function of the status id (`conditionEffectId`),
  16 letters and digits, and effects are stored under it, so it never changes.
- One condition's change on one field applies once. `countsOnce(effect,
  change)` (`roll-mods.mjs`) is the rule: a change belongs to the status of its
  effect whose system entry carries its key (none, or more than one, and it
  counts), and it counts unless an earlier active effect of the same actor, in
  `allApplicableEffects()` order, carries that status and a change on that
  key. It reads effects and never `actor.statuses`.
- libWrapper where present, otherwise a direct patch of the prototype, carries
  a wrap of the Active Effect class's `shouldApplyChange`: the wrapped answer
  first, a refusal standing, then `countsOnce`, and a throw logged with the
  wrapped answer returned. It is installed at `init` with the palette, because
  world actors prepare before `ready` and a later wrap would leave their first
  preparation counting twice. The module is its one owner. Every reader takes
  the same rule as the `admit` option of `orderedChanges`, so Foundry and the
  readers agree, and a step's condition is the status its change belongs to.
- The Armor Class waiver is judged per change, by that condition, so a waived
  charge alone leaves no step and a countercharge or a hand-set disorder beside
  it keeps one. A step the waiver spares on a character is still in the Armor
  Class the system folded, so the card's line lists it.

**Rejected.** The holder (the shipped `holdCondition` shape, and the new file
ruled before the owner's answer): the brought condition sits on a single-status
effect that a Token HUD click or `lift` deletes, so each needs the withdrawn
refusal or a re-create loop, plus hooks, a Judge-seat writer and a path for an
unlinked token's delta. A `preCreateActiveEffect` strip: it leaves a twin that
counts nothing. Suppressing the duplicate effect: an inactive effect adds no
statuses. Registering every `implies` as Foundry statuses: twenty-one static ids
and no figure gained.

**Cost.** The system's `getEffectModifierBreakdown` sums raw changes, so beside
a double its attack card lists both effects plus an "other effects" line of the
opposite sign; the total is right. An effect of one of these states made
before the entry took this shape holds one status and is not found by the
static id: its tile does not light, a click makes a new effect beside it, and
the old one is lifted by hand. Foundry's Token HUD lights the state's tile and
not the brought condition's, whose click adds a hand effect that `countsOnce`
gives no figure while the state stands. With the module off the merged effect
is still the system's own entry shape, unmanaged and deletable, and core
applies both entries' changes.

**Strongest counter, MEDIUM.** The filter decides, on every actor, whether a
change applies on an effect the module did not make, which is close to the
hand-toggle filter an earlier design rejected. Not HIGH: it stores nothing,
applies no figure and refuses only a second copy of one condition's change. It
is the method Foundry offers modules ("to introduce additional conditions under
which a change is applied"), and without the module every effect is plain
Foundry.

## 2026-11-25 — The rounds to a turn and the turns to an hour are units of measure and stay in source

A review during the Beastman work asked whether the rounds a dungeon turn
counts for time-keeping were a printed value, ruled that they were, and moved
them and the turns to an hour onto the importer (2726bf8d, ledger T-0730,
never released). A world with nothing imported then had no turn length and no
round length: round-level play advanced nothing, a spell duration counted in
turns had no figure, and a record counted in rounds never ended. Asked whether
to keep that, the owner:

"Too aggressive, rounds per turn is very generic rules, not IP"

**Ruled.**
- The rounds to a turn and the turns to an hour are stated in
  `lib/time-unit.mjs` as constants, beside the hour's seconds and the day's
  hours. They are not imported, no table declares them, and no reader of them
  answers null. The page reference stays (RR p. 263).
- The readers keep their names (`roundsPerTurn`, `turnsPerHour`,
  `turnsPerDay`, `turnSeconds`, `roundSeconds`, `timeUnitCite`).
- The importer's own copies of the turns to an hour read lib's constant
  (ledger T-0765).

Told the change would take the turns to an hour with it and no other figure,
the owner gave the test:

"If it is a generic concept that actual IP relies on to describe itself
mechanically, it's likely it doesn't need imported."

**Reading, the session's and not the owner's words.** The owner named the
rounds to a turn. The turns to an hour are taken with it: one sentence prints
both, a turn's seconds follow from the second figure alone, and a round's from
both, so restoring one would leave the world clock blank. Under the test both
are units the book's own procedures count in. This entry moves these two
figures and no other; the test is stated in `.claude/rules/ip-doctrine.md`,
and "likely" is the owner's word, so a figure that is not plainly such a unit
is put to the owner before its import or its constant is built. A
printed-value sweep that meets these two constants leaves them.

**Rejected.**
- The import with a constant to fall back on: one figure with two owners, and
  a table the importer would keep naming as missing.
- Keeping a Judge's override of either figure. The Ruledata Browser edits
  imported tables, and these are no longer tables; the override T-0730 gave
  goes with the import. The owner was not asked about it.

**Cost.** `ip-doctrine.md` said every number read off a page is content,
"however small and however alone", with no exception. It now carries the
owner's test beside that sentence, and the test needs a reviewer every time:
nothing mechanical tells a unit the rules are written in from a figure the
rules set.

## 2026-11-25 — Two generated stacks never merge, and a group's count is read when asked

Ruled where the beastman plan left the shape open. A stack the generator made
carries `gen: {part, cite}`, and a move compares it: the plan said to compare the
part where both carry one. Two gangs of one breed hold the same part over the same
base, so equal parts would merge the very rows the plan keeps apart. Two generated
stacks therefore never match, and a generated stack still merges into a plain one
over the same base. A group's count is read from its stacks and its nested groups
each time, in the place roster, the faction members and the location's headcount,
and a stored roster figure is no longer read for a group. A row whose group stands
inside another row's group counts none, since the outer count holds those bodies.
A row whose group does not resolve keeps its stored figure: a deleted group's last
known count stays visible, struck through. A formation member holding a group
deploys and recalls its tree, as a group token's combat does.

**Strongest counter, MEDIUM.** A formation member's cells now grow with nested bodies
the Judge may not expect, and the stored figure had the merit of being what a hand
wrote. Not HIGH: the figure was stale after any casualty, which was the defect, and the
formation already sized cells by the group's living count.

## 2026-11-25 — The chart's controls, and where its reader sits

Ruled where the beastman plan left the chart's shape open (docs/lib/ORGANISATION.md
is the mechanics). A send out writes the place's roster, then lets every other
roster that held the group go, then clears the group's parent: a group stands in
one place, and a stale second roster row would count its bodies twice. A recall
refuses where there is no group to go back under (a top row, a parent row with no
holder, a parent holder that is no group, a lone actor, which stands inside no
group) and says which; it is the one place a control answers a refusal, since the
write cannot be made. A press on an empty row makes its group in send out and in
leave alike, so no press refuses it.

A join and a leave are idempotent by key. A row the target already holds is the
first write having landed, so a second press writes no row twice and only
completes the clearing, and the faction's copy stands where the two differ. Two
writes with no transaction can stop between them; the faction answers, the view
marks the twin, and the Judge presses again, as moveStack's order leaves bodies
standing twice rather than nowhere.

The morale part from above is read from the units above a group, and an
ancestor's part counts only while that ancestor's officer is up (resolved, above
zero hit points, not marked dead). A group's own officer stays `commandMorale`'s
ungated term, as the henchmen engine writes it today. The reader lives in
`org-host.mjs`, apart from the writes, because the group's data model calls it and
the writes import the group's operations.

A faction's `affiliation` resolves each chart holder and drops one the world no
longer answers for, so `hasMember` and `headcount` agree that a deleted holder
affiliates nobody. A member row for the same actor wins over its chart row.

**Strongest counter, MEDIUM.** Gating the ancestors on the officer being up and not
the group's own gives one officer two rules: a gang's champion keeps leading at
zero hit points while the chieftain's part falls away. Not HIGH: the own term
predates the chart and the hire writes it from a cached figure, so a change is the
henchmen feature's to rule, and the owner's page reading (the part is the
chieftain's, and it ends with him) is the ancestor case alone. A recall that
refuses a top row may read as a gate; the alternative, writing nothing and
reporting success, leaves a group nowhere.
