## 2026-11-13 — An empty compendium id list is answered without the server (T-0353)

**Asked.** A timed import's abilities step made 4169 `getDocuments` calls for
729 item writes (importer DECISIONS, 2026-11-13, "An update pass costs a write,
not a library read"). Core makes two of them per compendium update, each asking
`getDocuments({_id__in: ids})` with `ids` empty for a document the pack already
holds (`ClientDatabaseBackend#loadCompendiumDocuments`, which guards no length),
and the server answers every compendium query by testing every stored document.

**Ruled.** `patches/compendium-empty-load.mjs` wraps
`CompendiumCollection#getDocuments` and resolves `[]` when the query's only term
is an empty `_id__in`, with no server call. Every other query, a `getDocument`'s
`{_id}` among them, reaches core unchanged. libWrapper `MIXED` where it is
installed, a plain wrap otherwise, as the token-light patch does. The patch
holds nothing, so it never answers for a deleted document, and every client runs
it, which also removes the scans other clients' writes cause. Lib owns it: the
method is core's and every feature's writes pass through it, so no feature's
folder is the owner; it is the only wrapper of `getDocuments` in the family.

**Rejected.** *Batching the update pass's writes per pack.* It spares one pass,
leaves every other bulk write and every other client paying the scans, and needs
a single-write retry for a chunk holding a document deleted mid-run. It is the
fallback if the patch is refused. *Skipping the call in the importer.* The call
is core's, inside `Document#update`.

**The counter-argument (moderate).** The patch changes Foundry for every caller
in the world, and a later core that gave an empty query a server-side meaning
would be bypassed without a sign. The match is exact (one key, an empty array),
the current server's `get` runs a plain scan that returns nothing for it, and
core can add the guard itself, at which point the patch is deleted.

*Cost:* a core release that changes what an empty `_id__in` returns is not seen
by the one caller shape this answers; the patch's suite pins the match and the
passes-through cases, and the live import count in importer TESTING, "Counting
reads", shows the loads gone.

## 2026-11-13 — A gate names a capability, and two providers of one do not stack

**Ruled.** A capability is what an ability lets you do, named independently of which ability grants it. Abilities declare what they `provide`; prerequisites, gates and stacking rules are written against the capability, not against one entry. The books print the same capability several ways (a skill, a proficiency, a class power, an alias under another name), and a gate written against one exact definition id misses the rest, where a `kw:` gate catches them all because each provides the capability. It also gives aliases and non-stacking one mechanism instead of two: two abilities that provide the same capability are the same capability twice, so they do not stack, and that falls out of the data rather than being asserted per pair.

## 2026-11-13 — A target-alignment scope is a gate or a sign flip, and they are different rules

**Ruled.** The books write two target-alignment scopes and they are not the same rule. A `gate` applies the bonus versus the named alignment and does nothing otherwise. A `sign` flips to a penalty of the same size versus everyone else.
**Rejected.** Storing either as the other, which is wrong by up to double the value in the direction that matters most.

## 2026-11-13 — A wear slot is an exclusion counted against magic items

**Ruled.** A slot is an exclusion, not a bonus: an item's form is mechanically irrelevant except that a character may not wear two magic items of the same form at once. `capacity` is therefore the magic capacity of the place, what `item-model.mjs` `slotUse` counts magic items against; what the body can physically carry twice is a second count there, where armour and weapons take a place and clothing and plain gear take none. `capacity: null` is unlimited, and the belt and the back are uncapped because several different forms hang from each. A slot assignment that is slightly wrong costs only mis-scoped exclusivity, which is why gear may declare its slot as a correctable guess.

## 2026-11-14 — The command capacity is read off the page, all three rungs

**New evidence.** The archived 2026-09-22 entry "The squad command-capacity figure is an interpretation, not a printed number" (in `DECISIONS-through-v11.14.5.md`) held the first-level rung to be unprinted. RR p. 169, the Mercenaries section's bullet on personal leadership, prints three rungs, each a minimum leader level and a count for infantry and a count for cavalry, the first level's among them. The mounted count is not half the infantry count at every rung. That entry is superseded, and it has no row under "In force" to change.

**Ruled.** The module holds no level and no count of that ladder. A `proseValues` recipe, `wages.commandCapacity`, reads the nine figures from the Judge's own copy (`importer/table-recipes.mjs`); `henchmen/rules/wages.mjs` `commandRungs` turns them into rungs; `group-logic.mjs` `platoonCapacity(level, rungs)` answers the highest rung whose minimum the officer meets. Three states stay apart and each shows differently:

- Nothing imported, or any rung unreadable: no status and no warning at all, and no "not imported" text. The table is taken whole or not at all, because a ladder with a rung missing would rank an officer below every rung they in fact hold.
- An officer under the lowest rung: over-command, as the 0th-level case was, with a message that names no limit.
- A rung in force: the unit is compared with it, and the warning names the rung's two counts.

**The session's call, owner may overrule: a unit of both arms.** The page states nothing for a mixed unit. Infantry and cavalry are each held to their own count of the rung in force, and a unit with both is over when the infantry's share of its count plus the cavalry's share of its own passes one, which reproduces the page exactly for a pure unit. `troopStrength`'s doubling of mounted bodies is gone, since the page's cavalry count is not half the infantry's. A reversal (a mixed unit over only where either arm alone is, or where a Judge's own rule of conversion applies) changes `group-logic.mjs` `commandStatus` and its two suites, and nothing imported.

**Rejected.** Keeping the first rung as an interpretation beside the two printed ones; converting cavalry to infantry-equivalents at a fixed ratio, which the page's own counts contradict.

*Cost:* the group's `troopStrength`, `commandCapacity` and `overCommand` getters are removed for `troopCounts` and `commandStatus(rungs)`, so lib `apiVersion` is 45. A world that has not imported the Rules tables hires an over-large unit with no warning.

## 2026-11-17 — The tracker fires the turn hooks and lifts a record by its turn count

Spell effects that last a combatant's next turn, or a few rounds inside one
fight, need an end the world clock cannot give: combat does not move this
system's clock, and the tracker's initiative is rerolled each round, so counting
the fight's rounds is wrong too. The owner's words: "cast time and spell duration
(and if it requires concentration to hold) are the other obvious buckets to
think about", and "1 stops", a record that runs out stops applying by itself,
with no card offering its removal and no press waited for. Ruling 94 of the
spell-effects plan puts the turn handling in lib and qualifies the cost line of
magic DECISIONS 2026-11-11 (the clock math), "a combat's rounds do not age a
record": a record carrying `flags["acks-extras"].turnLife` is aged by the
tracker's turns, and the clock math stays for every other record.

`status-effects.mjs`, the one owner of the tracker's turn handling, fires
`acksExtras.turnBegan(combat, combatantId)` and `acksExtras.turnEnded(combat,
combatantId)` on the primary GM, with the handling of a round that opens before
its initiative is rolled it already had, and deletes by id a record whose
`turnLife` count is reached at its edge (`start`: at that turn's start; `end`:
at its end). Pure `turn-life.mjs` decides, so the rules are tested offline.

*Rejected:* magic listening to `combatTurnChange` itself, which is a second
owner of the rounds-before-initiative reading and the primary-GM gate;
counting the combat's rounds, since initiative is rerolled each round; lib
listening to its own hooks, which would order the lift after a listener that
should find it done. *Counter (medium):* one write per turn per record. An
`end` record costs a `seen` update at its begin and a delete at its end; a
`start` record's last turn is one delete.

*Cost:* a deleted fight leaves its records, ended by their flag clock. The
hooks fire for a turn the Judge passes over by hand in an unrolled round, since
lib already lifts there, and the conditions still lift on a step back where the
hooks and records do not count. Magic's own turn-end detection is unchanged
until the ROADMAP row moves it onto the hook.

## 2026-11-17 — One reader for a record's parts: narrow, test, then resolve

**Ruled.** The owner: "a second spell record of the same kind leaves one figure,
the larger, which stays until the last record ends" (owner ruling 2), and
"automation with transparency is the design principle". Example: two records
each give a bonus to one proficiency's throw, +3 and +2; the throw takes +3, the
+2 is told as yielding, and when the +3 record ends the +2 stands. Governed by
the spell-effects plan's rulings 75 to 82 and 130 to 140 (S5a, the lib half).

- **`recordParts` is the one reader** of a record's parts for every roll the
  attack seam does not make, `ROLL_MODS_ON` gaining `throw`, `reaction`, `grant`
  and `immune`. It narrows by `ref`, `rollKey`, `saves` and `attackKinds` BEFORE
  `resolveStacking` (ruling 130, which amends 76 and 80): every spell part provides
  `kw:spellrecord`, so a larger part for another roll would otherwise take a
  smaller part's place. A part with no figure never reaches the stacking, apart
  from a `grant` and a `throw` of mode `auto`. *Counter (low):* an ordering
  contract a later edit could break; the suites pin it with a larger part that
  misses the roll.
- **A narrowing the caller named nothing to test is `pending`**, never applied:
  a part with `saves` read by a roll that names no save, or a `ref` with no
  `subject`. *Rejected:* treating an unnamed narrowing as no narrowing, which
  adds a Death-only figure to every save. *Counter (medium):* a caller that
  forgets an argument gets silence plus a pending row.
- **A `set` figure is oriented by the throw's type**, which lib does not know:
  `rollType` `below` makes the higher target better, any other the lower.
- **`EFFECT_MODES.auto`** (ruling 131) is a part with no figure whose bearer's
  throws of that ref resolve `auto`, answered as `outcome: "auto"` (the word a
  rung's outcome already uses). *Counter (medium):* "unimpeded" may mean speed
  only (owner question 1c.20).
- **An armour class set by the kind of attack** (rulings 80, 133) is a lift on the
  attack against the bearer: `max(0, figure - (ac.value - dexMod + conditions))`,
  the DEX read out only for a character. It joins the add parts in one
  resolution. *Rejected:* writing `system.ac.value`. *Counter (medium):* a shield
  counts as armour (1c.23), and a set below the target's own armour class is a
  told yield, never a floor.
- **A saving-throw part under a gate** (ruling 81, 134) is tested through
  `partHolds`, and a row of the spell's own save (`ownSave`) is tested per
  saver. This supersedes, for gated save parts, 2026-11-16's "only the unscoped,
  ungated parts". New evidence: this is the first save part to carry a gate (the
  enervated daily save), and a plain status gate would add the figure to an
  enervated creature's Death save against poison, so the gate is marked
  `occasion` and waits for a roller to name it. *Counter (medium):* no module
  roller names the occasion yet, so the figure only ever shows as pending.
- **An immunity a record grants** (ruling 135) is an `immune` part read by
  `recordImmunity`; `actorDefenses` is not widened. *Counter (low):* a second
  immunity source.

*Cost:* lib `apiVersion` is 58. Every reader tests a part against the live
effects at its roll, so a part is gone when its record ends. The editor controls
for the new row fields wait for the approved design.

## 2026-11-18 — One register of what a character can cast: lib owns it

**Ruled.** The owner: "Pale when not cast and can cast on self. Gold when cast on
self even if by another." "That includes from scrolls in inventory FYI, they
should share an awareness register." "Inferred correctly, can't cast does not
show as can but uncast". Example: a mage carrying a grant spell with a slot to
spare has no record of it, so the granted roll is pale; a cleric casts it on her
and it is gold; a fighter holding the same spell item has no row. Governed by the
spell-effects plan's "The castable-spell register (architect, 2026-11-18)".

- **The register is `lib/spell-sources.mjs`**, shaped like
  `registerItemBonusSource`. Its readers (the abilities feature now, the cast
  dialog later) cannot import magic, and a second source was named: lib owns the
  seam and each provider registers into it. A source (`registerSpellSource`)
  answers what one place holds; the reach (`registerSpellReach`) has one owner,
  magic, which decides what a cast writes on its caster. `castableSpells` merges
  a spell two sources hold by a row's own order of naming (cookbook id, uuids,
  folded name) and the source with the better capacity speaks for it.
  *Rejected:* a magic-owned reader that abilities imports, which inverts the
  dependency. *Counter (medium):* the reach is magic's logic reached through lib,
  so a second reach owner would silently replace the first.
- **It extends `recordParts`, never forks it.** `recordParts` gains an `entries`
  option (default `rollModsOf(actor)`), and `availableRollMods` returns the on-self
  parts in that entry shape, so an available grant is narrowed by `ref`, skipped
  by `hasCapability`, tested by `partHolds` and stacked exactly as a recorded one.
  This qualifies 2026-11-17's "One reader for a record's parts", whose reader
  took records only, and supersedes in part the spell-effects plan's ruling 78
  "Readers" and `grantedThrows`' "while that record lasts", both under 7 days
  old. New evidence: the owner's rulings above. *Counter (low):* callers must pass the recorded entries first for
  a recorded grant to win a tie, which only an ordering contract holds.
- **On self** means a cast would write the part on the caster: an `aimedAtSelf`
  row, or a row aimed at a target, recipient or area under a blank, self,
  creature, recipient, hdPool or area model that the target gates admit. An
  object or structure model answers false, special null. *Rejected:* reading
  "can cast" alone, which shows a row for a spell that would write nothing on its
  caster. *Counter (medium):* the register answers what a cast could write, so a
  pick group counts every option.
- **No seat, no cache.** No reader tests `isOwner`: Foundry gates no read, so a
  seat-dependent answer differs for no reason a user can name, and a source
  decides what a non-GM `viewer` may be told. The register keeps nothing between
  calls; the twin lookups are one lazily built map per `castableSpells` call.
  *Counter (low):* the library is read once per call rather than once per change.

*Cost:* lib `apiVersion` is 59. The scroll source waits for a spell pointer on a
scroll (owner question 1c.27); until a source registers for it, a scroll adds
nothing to the register.

## 2026-11-18 — The invocation level is a spell-domain scale, and a row's gate is a range

The owner, on By This Axe's requests R1 and R2: "(b) spell effects adds it."
Architect rulings 200 and 201 (the spell-effects plan) place the lib half here.

- **A scale, not a new LevelValue kind.** `VALUE_SCALES.invocationLevel` with
  `domain: "spell"`, so `resolveLevelValue(lv, level, scales)` keys a
  `conditional` on `scales.invocationLevel` with no change to the resolver, and
  the importer's paired-ladder locator already builds a conditional on any
  `on`. `valueScalesFor(domain)` is the picker's list; the ability roll editor
  offers `"ability"`, since a roll has no cast to supply the level. *Rejected:*
  a `kind: "invocation"`, which every consumer of `VALUE_KINDS` would then
  have to learn. *Counter (low):* a stored roll naming the scale still
  resolves to null, silently.
- **A gate is a range.** `invocationFrom` and `invocationTo` are nullable
  whole numbers on `effectField`, inclusive on both sides, a blank side open.
  *Rejected:* a lower bound only, since a higher level replaces some rows.
  `rowInInvocationRange` reads a side by `Number.isInteger`, never by
  coercion, so a stored null is open and not 0. With no level set a gated row
  is out and an ungated row is in. *Counter (medium):* "no level, gated row
  out" hides a bounded row from a cast that never chose a level, which only
  the cast dialog's level choice (R3) and its verdict keep from being silent.
- **Where it is read.** Magic reads both, resolving the scale once per cast
  (the plan's rulings 200-202); lib supplies the helper and the fields and
  reads neither itself.

*Cost:* lib `apiVersion` is 60.
