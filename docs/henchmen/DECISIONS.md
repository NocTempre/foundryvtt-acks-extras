## 2026-11-14 — A market hire's morale base is a troop's imported figure or none — SUPERSEDED IN PART 2026-11-14

Owner rulings behind it: a printed figure is imported, and "missing imports stay
blank" with the page as the clue. A market hire used to store a base of zero for
every kind, which stood in for the bases the page prints by kind (RR p. 166) and
kept core's own morale field from ever being read.

- `morale.base` on the record is nullable and starts null. A mercenary hired from
  the market takes its troop type's imported `wages.mercenaryWages` figure
  (`rules/wages.mjs` `hiredMorale`), read by the type its wage row is keyed by
  (`wageTroopType`: the combined composite/longbow entry resolves to the
  settlement's variant, as the market's own wage lookup does). Every other kind,
  and a troop whose figure is unread, records null.
- Null reads as the sheet's own morale field: `moraleParts` reports `from:
  "record"` or `"sheet"` and the Service panel's base tooltip names the sheet's
  field when the record holds none. Zero stays a figure: only null defers.
- **Not done, the specialists' printed bases.** Their record base stays null, so
  a hired specialist reads the sheet's field; the paragraph the `levelMorale` and
  `officerMorale` recipes window prints them, and no recipe reads them yet. The
  ROADMAP row that carried this went with the row this entry closes; the
  remainder is this sentence.
- **Not done, the starting loyalty (stopped).** The page prints the start per
  kind, but core's `retainer.loyalty` is a non-nullable integer that every
  loyalty reader and the four `syncLoyalty` writers fill with a number, so a null
  start has no figure to write there without choosing one. The stored zero stays,
  and its ROADMAP row stands.
- Rejected: reading the specialists' and officers' bases in this change, and
  leaving the stored zero where a troop's figure is unread (the zero is exactly
  the stand-in). Cost: a record written before this change keeps its stored zero,
  with no migration.

## 2026-11-14 — A hire's starting loyalty is the figure an import read, or blank

Supersedes in part the entry above: its "Not done, the starting loyalty
(stopped)" bullet. Owner rulings behind it: "Dix so loyalty can be blank" (read by
the orchestrator as "Fix so loyalty can be blank"), "caught printed values are
fixed on the spot", "a figure a page prints is imported" and "missing imports stay
blank with a page reference as a subtle clue". **New evidence, since the entry is
under a week old:** the owner's ruling this day, and a probe of the installed
Foundry 14 common code: core's `retainer.loyalty` declares a `NumberField` with no
`nullable` option and the field's default is nullable, so null cleans and
validates. The "stopped" bullet rested on the opposite premise. Core's only code
reader of the field is `Actor#rollLoyalty`.

- **Where the blank lives.** The record's `loyalty.start` is nullable; null is no
  figure and zero is a figure. Every module hire writes into core's field the
  effective score or an explicit null (`adapter.setLoyalty`, after the record is
  written), so the field and the record agree and no figure left by the sheet or
  an earlier employer stands in. A hire's own create data and `setRetainer` carry
  `loyalty: null`.
- **The start, by kind** (`rules/loyalty.mjs` `hireStart`, resolved at hire as
  `hiredMorale` is): a mercenary officer takes `wages.baseLoyalty` (RR p. 171,
  which had no reader), every other hire `influence.loyaltyChanges.start`
  (RR p. 166), and a captured monster keeps the Irrefusable Offer or
  forced-servitude start. Élan adds only to a start that was read. Followers of a
  class and ruffians are printed with starts but nothing hires them, so they have
  no key; the followers ROADMAP row stands.
- **Level gain and calamity are printed figures** and had been written into
  `events.mjs` as literals. They are `loyaltyChanges.levelGain` (times the levels
  gained) and `.calamity`. A figure that was read records its ledger entry even
  while the start is blank; one that was not records no entry, as the unread
  morale bumps do. `WOUND_PENALTIES` stays in source under its own ROADMAP row.
- **Blank against sheet.** A record with no start reads the sheet's Loyalty field
  when it holds a number the module did not write (a hand entry, or a hireling
  `enrollNewcomers` adopted), as the whole score, labelled "set on the sheet".
  `adoptSheetLoyalty` turns that figure into a start (the score less the
  permanents counting, the employer's Charisma and powers, the back-calculation
  `enrollHenchman` already does). It runs before `addLoyaltyPermanent` appends,
  and from the actor-update watcher when the field changes by hand; the module's
  own writes carry `LOYALTY_WRITE_OPTION` and the watcher skips them. A hand edit
  made while a start is recorded is overwritten at the next sync.
- **Rolls refuse.** A hireling with no score is refused with a warning naming the
  sheet's Loyalty field, never rolled as if a figure were printed: a guard at the
  top of `openLoyaltyRoll`, and lib `patches/loyalty-roll.mjs`, the one wrapper on
  core's `Actor#rollLoyalty`, since the Service panel's own row, core's header
  button and hireling list, the monster sheet and the Follower Card all end there.
- **Surfaces.** The Service panel's figure and start part, the roster's value and
  title, the Rolls tab row, the Stats tab field, the Follower Card and the
  Statblock row show nothing and carry the page reference as their tooltip
  (`lib/score-bounds.mjs` `blankLoyaltyCite`: the imported table's recorded page,
  else the page that prints the figures). No "not imported" text.
- Rejected: working the start out at read time (it breaks the morale ruling's
  fix-at-hire and leaves core's field blank after an import); leaving core's field
  unwritten for an unread start (a stale figure would roll as printed); refusing
  only at module call sites (the Service panel's row ends in core's method).
- Cost: a record written before this change keeps its stored zero, with no
  migration; a world that imported `loyaltyChanges` before the three new keys
  existed records no start, level-gain or calamity entry until it re-imports; a
  pre-module hireling whose field holds core's initial figure reads as set by
  hand; an officer's start reaches the record but `keepsLoyalty` still draws a dash
  for a non-henchman (2026-10-23).
- Not done: `scripts/lib/data/group-data.mjs` `unit.loyalty` keeps its stored zero
  (ROADMAP row). Registered for correction: the monsters 2026-11-14 entry says
  core's `attack.throw` has "no null"; the same field default makes it nullable.

## 2026-11-14 — A market with no known class posts, rolls and charges nothing

With the class unknown (`docs/location/DECISIONS.md`, "A market's class is the
Judge's or the table's, and otherwise unknown") a null would have clamped to the
largest market, so every reader answers null before a clamp. These are the
session's calls, owner may overrule:

- **`createPosting` refuses `no-market-class`, silently.** The code joins the
  dialog's silent refusals (a refusal that only names a missing figure shows no
  toast). A Judge's placement that names its level rolls and charges nothing and
  goes through.
- **A month is deferred like an unloaded registry.** `processLocation` keeps the
  market it holds and rolls nothing, as in "A month roll never fires against an
  unloaded table registry"; that ruling stands and this is one more condition.
- **A weekly fee for a posting at an unknown class is skipped, not refused.** A
  refusal closes the posting and warns; the class is not the employer's fault.
  The weeks owed are charged when a class is set.
- **A directed re-roll with no class keeps the posting's results** and does not
  purge them.

*Cost:* a search posted while the class was known and run on after the Judge
clears the class pays nothing for those weeks and then the arrears.

## 2026-11-14 — The followers' arrival level is read from RR 334, and a level the tables did not print is left off

Owner rulings behind it: a printed figure is imported, and "missing imports stay
blank" with the page as the clue. The followers dialog compared the character's

- **A `followers` document with one table, `arrivalLevel`.** A `proseValues`
  recipe on RR 334 reads the figure after the clause that names the arrival, so
  the source holds an anchor and no figure. It sits in a document of its own

  carry unrelated figures.

  document now exists in every world that imports the Rules tables, so
  `hasDoc("followers")` would pass and the dialog would throw on the first
  missing table. It returns at once unless `arrivalLevel` and the four tables
  are present (`rules/followers.mjs`). `tools/validate-producers.mjs` waives
  the four tables one by one in place of the whole document, against the
  narrowed ROADMAP row; the producer itself is not built here.
- **Only `arrivalLevel` is declared with `expectTables`, and `followers` is not
  added to `RULEDATA`.** The declaration is the import surface, so it names what
  an import can supply; announcing the document at `ready` would tell the Judge
  to import for a roll that stays off until the four tables arrive, which is
  the case "The ready-time table check names only ids an import can supply"
  rules out. Add the id when the four tables have a recipe.
- **The level notification states the imported figure.** It interpolates the
  arrival level and the page `citeOf` records, the page alone being absent for a
  Judge's override. No figure is in `lang/`, and the sentence about a stronghold
  it carried is gone.
- **A level the tables did not print is left off, never filled.** A troop grant
  with no printed level reads without one, and a companion line lists only
  printed levels. A failed bracket lookup on the companion roll no longer stands
  in a first level.
- Rejected: a producer for the four tables in the same change (its own ROADMAP
  row); keeping the old literal as a default for a world without the import (a
  default is the value the ruling removes). *Cost:* no world sees a change until
  the four tables are imported.

## 2026-11-14 — The followers' platoon size is read from RR 335, and a platoon count waits for it

Owner rulings behind it: a printed figure is imported, and "missing imports stay
blank" with the page as the clue. The followers dialog divided a troop grant by
a literal to count the troop type rolls. These are the session's calls, owner
may overrule:

- **A second table, `platoonSize`, in the `followers` document.** A
  `proseValues` recipe on RR 335 reads the figure inside the bracket after the
  unit's name in the sentence that sends the Judge to the troop type table once
  per platoon, so the source holds an anchor and no figure. It is declared with
  `expectTables` beside `arrivalLevel`, and the recipe is its producer.
- **It is not in the dialog's gate.** The roll still opens on the arrival level
  and the four tables; an unread size costs the troop line its platoon types and
  nothing else, since the count of troops, the companions and the apprentices do
  not depend on it. A line that lists no types is the blank, and no count of
  platoons is made without the figure. Example: a world with the arrival level
  and the four tables but no platoon size posts "40 × troops" with no type
  rolled; with a size imported it posts the same line and the types.
- **The floor of one is gone, and its reading is structure replaced by the
  page.** The old `Math.max(1, …)` made a grant of no troops roll once. The page
  prints a roll for every platoon and for a part of one, which is the round-up:
  any positive count rolls at least once without a floor, and a count of zero
  rolls none. The floor guarded only the case the page does not cover, so it was
  an invented rule and not procedure.
- **The troop type die stays a literal here, and moves with its table.** The
  die of the troop type table is printed with the table itself, a table no
  recipe reads (ROADMAP, "Four followers tables have no producer"), and the
  sibling `companionLevel` table carries its own `formula`. Reading it from the
  rows' spans would stand on a shape nothing yet produces, so it is left for
  that table's recipe, and the ROADMAP row says so. *Cost:* the card's label
  and the roll still carry a die.
- Rejected: gating the dialog on the size (it would switch the roll off for a
  figure that touches one line of the card); keeping the size as a default for
  a world without the import (a default is the value the ruling removes).
  *Cost:* no world sees a change until the four tables are imported.

literal formula six times and cited RR 168, which only says henchmen are rolled
up like player characters. The player-character method that page points to
(RR ch. 1) is an allocation with different formulas and floors for different
attributes and a choice of which gets which, so it is not what the code did.
The Judges Journal's 0th-level NPC attributes list prints a roll-in-order
method and names it for henchmen prospects: the literal was a printed value
cited to the wrong page. These are the session's calls, the owner may overrule
them.

- **The formula is `people.hirelingAttributes`**, a `proseValues` recipe on
  JJ 252 that reads the printed formula with an anchor that carries no figure.
  `rollAttributes` throws it once per attribute in the sheet's order and answers
  null where the table is unread or the formula is not of the shape `NdM`; the
  hire then rolls and records nothing and creates the hireling with the sheet's
  own scores. Example: a world with the table imported hires a candidate with six
  recorded scores; a world without it hires the same candidate with none, and
  the Service panel shows no score row.
- **The recipe is read for every hire, not only 0th level.** The page sits in
  the 0th-level section and names henchmen prospects, and a leveled prospect is
  a henchman too, so one formula serves every candidate as it did before. The
  page sends a stronger character to the player-character options, and a
  leveled candidate is rolled like a prospect here. The owner may rule the
  formula 0th-level only, with a leveled hire recording none. *Cost:* a leveled
  hire's scores come from the prospect's method.
- **The page's optional swap is not done.** It is the Judge's call on scores
  the Judge sees, so a hire records the roll as made and the Judge edits the
  sheet.
- **The order stays the module's.** The attribute keys and their order are the
  sheet's structure; the page's list is in the same order.
- Rejected: reusing core's Scores Generator formulas (they are `data-formula`
  attributes in a template, not a system export, and the method they belong to
  is an allocation an unattended hire cannot make); making the hire read the
  campaign's chargen method setting (the per-attribute choice has no one to
  make it at hire). *Cost:* no world rolls attributes at hire until the people
  tables are imported.

## 2026-11-17 — A hire states its wage monthly, and an old group is keyed by a repair check

- **Payroll bills a month, so a hire writes a month.** A specialist's
  availability row carries the unit its wage was printed in, and the candidate
  keeps it for the row's display. `hire` and the offer dialog convert a day or
  a week figure to a monthly one (`rules/wages.mjs` `monthlyWage`, by the
  market month's length in days); a unit it cannot convert is left blank for
  the Judge, since a figure billed as monthly in its place is wrong.
- **Groups hired before the wage type was stored are repaired, not billed by
  guess.** `henchmen.wageType` finds a mercenary group's combined
  composite/longbow stack with no `wageType` and stores the variant of the
  settlement the group was hired at. A group whose settlement is gone is listed
  and left alone: its variant is not derivable. Rejected: a billing fallback
  that reads the variant at payday (a settlement's variant can be edited, so
  the figure would move under a group already hired) and a migration run
  unasked at ready (a write the Judge did not choose). *Cost:* an old group
  stays unbilled until the repair tool is run.

## 2026-11-24 — A company's unit block rides its create; a troop prototype still bypasses the system's create

**Ruled.** `findOrCreateGroup` passes the unit block (category, employer,
location, command level) as `system` in the one `Actor.implementation.create`,
and the follow-up `group.update` that restored it is gone. `lib/group-encounter.mjs`
`makeEncounter` likewise passes no `items: []`. A troop prototype is still made
through the base `Actor.create`: its reason is now the system's `isNew` flag and
coin seeding for a character, and no longer the loss of `system`.

**Why.** `acks` 14.2.0's `AcksActor.create` keeps the caller's `system`

group's create-time `system` survives the override. A character created without
`items` still gains `isNew: true` and the money rows of the equipment pack, and a
stack's `template.snapshot` is the prototype's `toObject()`: every body minted or
detached from it would carry the flag and the coins, and a detached henchman's
sheet would offer Generate Scores.

**Supersedes, in part,** "A troop prototype is created through the base
`Actor.create`" (2026-09-30, DECISIONS-through-v11.14.5.md, In-force row above):
its premise that the override replaces create-time `system`, and its line that
the post-create update stays. The base-class call it ruled stands. The new
evidence is `acks` 14.2.0's `AcksActor.create`.

**Rejected.** `Actor.implementation.create` for the prototype, with the flag and
the coin rows cleared in a second write: a parallel path around what the base
call already avoids.
