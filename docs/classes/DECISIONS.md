## 2026-11-13 — a language's descent is not read, and written-word powers belong to the ability model

**Ruled.** A language may record its parent for flavour, but nothing in the classes feature branches on it: no rule grants partial comprehension of a parent tongue or a bonus for a sibling. What lets a character get sense out of a language they do not speak is a written-word power a character either has or lacks (Deciphering, JJ ch. 12; Loremastery, RR ch. 3). Neither is a slot, and neither cares which tongue descends from which, so both live in the ability model and nothing about them lives in `languages.mjs`.

## 2026-11-14 — A weapon narrowing with a figure unread is unpriced, never priced at a stand-in

**Ruled.** The builder's weapon-narrowing penalty prints two figures in one sentence (JJ p. 292): the fighting value it starts from and the experience added per power gained. `assembleBuilderTables` reads both through the `tradeoffPenalty` recipe, and a trade-off's benefit through its own row. With any of the three unread, a weapon row's `xpDelta` is null, and a row's `powersGained` is null where its benefit is unread (it had fallen to 1, and the penalty to 0, which priced the row at zero or at one power's worth). `baseXpCost` charges a row only when `xpDelta` and `xpDeltaMinFighting` are both numbers and the build's fighting value reaches the second; the power summary already counted a null as no power. A row that is not a weapon narrowing is priced at zero by structure, as the page states.

**Rejected.** Pricing a row whose threshold is unread at every fighting value, which is what the earlier consumer did with an absent threshold. **Cost.** The assembled rows are stored with the raw reads (`assembleBuilderImport`): a world that imported earlier keeps its stored rows, with the threshold they were written with, until an assembly runs again, and that assembly, working from raw reads that hold no threshold, leaves every weapon row unpriced until Rules tables are re-read; there is no migration (owner, 2026-11-11: no tools for earlier-version data).

## 2026-11-14 — An import leaves an elected damage bonus unmade, and the next hand apply asks

**Ruled.** The owner, 2026-11-14, on an import that stopped at the election's dialog with nobody at the keyboard: "Must be unattended". A cookbook import of a character applies its class with `unattended`. Where the class's column is elected and the character holds no answer, `readyToApply` asks nothing and reports the election as owed: the class binds at the printed level with everything else it grants, no damage bonus is written to either side, and the flag carries no `damageBonus`. Nothing is recorded as answered, so the next apply by hand (the picker, a dropped class, a gained level) asks as it always did. The open election also shows on the character sheet's Class tab as a Damage Bonus row with an empty select, and choosing there (`electDamageBonus`) writes the one side's bonus at the character's level and records the answer; an answered row is read-only, the choice being for good.

This qualifies "only a class that leaves the choice to the player asks for it" (2026-09-04) and "an unqualified damage bonus is elected by the character, not assumed" (2026-08-27): a hand apply still asks and nothing is assumed, and an import no longer asks.

**Rejected.** Reading the election off the character's page: the stat block prints a damage total that folds several terms, and no line says which side was chosen, so a side derived from it would be a guess written as an answer. Defaulting to one side or to both: an invented election, and one the flag would then refuse to re-ask. Holding the dialog to the end of the import: still a dialog an unattended run stops at. Making unattended the default of `applyClass`: every hand path would stop asking. The Judge's own sheet import (the character sheet's PDF import) keeps asking, since a Judge runs it for one character and is there to answer.

**Cost.** An imported character of such a class rolls damage without the class's bonus until someone elects on its Class tab or re-applies the class by hand. A new import path that applies a class without `unattended` asks again; `tools/test-class-unattended.mjs` pins the cookbook path.

## 2026-11-15 — A kit links one shared library, and a skin is minted once

**Reported.** A world's Item library held "Waterskin" 33 times and "Backpack" 34 times under `Class Templates / <Class>`: every class's package minted its own copy of every kit item. The owner, 2026-11-15: "It was done on purpose <- misread, the item should be shared. I think you misunderstood the rule to build individual flavor variants, but the pre-skinned root item or identical entries should be shared." And: "Seems like dedup in general on kits is an issue. Kits contain links to items, sometimes a new skin version that gets registered as a new variant, but the library of items is shared not duplicates". Example: two classes that both print "mossy kitshare tunic" link one tunic skin, and the class that prints a bare "kitshare flask" links the imported flask itself.

**Ruled.** A kit links one shared library; a skin is a new variant of it, minted once.

- **Predicate.** A gear entry is plain (`isPlainBase`) when its name, with the count off it, equals its base's name or the base's plural (`plainNameMatch`, folded, no slash or comma variants), it carries no skin name, and it prints no price other than the base's. A plain entry whose base the library holds (a sidebar document or a library shelf's, the rule `findSource` already answers as `linkable`) links the base itself, and the bundle row carries the quantity: "Torches" ×6 links the Torch with quantity 6.
- **Keys.** Everything else is a shared part, found by a key before one is minted (`sharedPartKey`). Gear: the base's ref (else its uuid, else `root:<type>` for an item built from the equipment root), the skin name, the printed price. A specialized ability copy: the definition's ref and the selection. A spell copied from a compendium outside the library: the definition's ref. `planKitEntry` answers link, reuse or mint.
- **Flag.** A shared part keeps `flags["acks-extras"].templatePart`, whose many readers test only that it is there, with the shape `{kind, key}` and no class identity. Bundles and tables keep `{classUuid, classKey, kind, band}`. No count of classes and no list of them is stored.
- **Scope.** Reuse stays on the class's side of Remove Imports: a class on a library shelf reuses any shelf's part, every line included; a sidebar class reuses sidebar parts. One key-to-uuid map is built per `materializeTemplates` call from the loaded library and the shelves' indexes, and each document the call creates joins it.
- **Folder.** Shared parts are minted on the package's own Item shelf in `Class Templates / Shared`. The importer passes the folder (`sharedFolder`); the sheet's own build defaults to it on the same shelf or in the sidebar.
- **Detach.** A shared part has no class identity, so `detachTemplatePackages` never matches it: detaching a class deletes its bundles and table and leaves the shared parts, which other classes link. A part an earlier build stamped with a class is deleted as before.

This supersedes in part "a template naming a sword copies the imported Sword" in 2026-08-20 and the cost paragraph beneath it (a world copy per package), and the placement of skins and copies under `Class Templates / <Class>` in 2026-09-10; bundles and tables stay there. It qualifies 2026-08-19: the documents are still real and repairable, no longer independent per class. 2026-08-30's premise, a copy per class, no longer holds; its predicate, a pick list offers definitions only, stands.

**Rejected.**
- **A count of the classes using a part, found by scanning bundles.** `libraryItems` sees the documents loaded; a shelf not yet loaded answers with less, so a scan undercounts and a part still linked would be deleted.
- **A list of classes on the part.** A second authority beside each bundle's `itemList`, to be kept in step by every edit a Judge makes there.
- **`Variants` as the folder's name.** 2026-08-22 ("the word is paths, not variants") keeps "variation" for equipment qualities, and this folder holds more than variants of gear.
- **Filing a skin beside its base.** The folders are the importer's, and the base may sit on another line's shelf.

**Cost.** A world needs a fresh import to get the shared shape; owner (2026-11-11) ruled no tool serves earlier-version data, so old per-class parts keep working as they are and a re-import does not look for them. A Judge can no longer repair a skin for one class only: the edit reaches every class linking it, and a class-only change is made by duplicating the skin onto that class's bundle. A sidebar homebrew class's links to bases that sit on a library shelf go missing after Remove Imports, as its links to any shelf document did before.

## 2026-11-17 — A casting row's level cap is its own key

**Ruled.** A casting row names the ladder that limits what the tradition can reach in `levelCap`, and `casterLevel` stays the ladder (blank: the class level) that says how strong a cast is. The two gnostic rows in the By This Axe register set `levelCap` to the maximum-invocation-level ladder and leave `casterLevel` blank. The capacity strip (`casting.mjs` `poolState`) reads `levelCap`; the cast engine reads `casterLevel` only.

**Evidence.** BTA p. 120 treats the cap and the caster level as separate axes. The earlier rows set `casterLevel` to the cap ladder because the strip had one key to read, so the cast engine resolved a gnostic caster's level as the invocation cap.

**What it changes.** For a gnostic caster the cast engine's caster level (`magic/cast-level.mjs`, source `"ladder"`) becomes the class level (source `"class"`), which is what the printed page says and what per-level durations scale with. The strip's figure and the vancian rows (RR arcane, whose `casterLevel` ladder is a real caster-level lag) do not change. The cast engine does not yet read `levelCap`; the invocation-level choice in the cast dialog is the magic lane's slice.

**Rejected.**
- **Falling back to `casterLevel` when `levelCap` is blank.** No other compiled row names a ladder in `casterLevel` on a tradition with neither slots nor a pool, so the fallback would serve nothing and would keep the two axes tied for a homebrew row.
- **A migration of worlds that hold the old rows.** Earlier-version data is not served (docs/DECISIONS.md §29); repairing the Classes shelf in place (docs/guides/classes.md, "Keeping documents current") rewrites the two rows.
