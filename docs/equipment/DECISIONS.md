## 2026-11-13 — The draw and the attack wait for the weapon rows

**Ruled** (owner, on T-0521 and T-0522): the load window, in which the weapon
rows are not yet published, is "A defect; fix it" — "The draw and attack paths
wait for the weapon rows. T-0521 and T-0522 are fixes in P3b; the ability-training
walk waits too". An example: a two-handed weapon drawn a second after a reload
takes both hands, as one drawn a minute later does, and an attack thrown then
carries the Non-proficient row the same attack carries later.

**Decided.** `rowsSettled()` (`weapon-rows.mjs`) is the wait an action takes, and
it is bounded (`ROWS_WAIT_MS`): the publication lands with zero rows in a world
that imported none, so that world settles at the load, and one that never lands
releases the action with a warning rather than hanging it. The wait is placed
where the action starts, not at each reader: the draw writes (`drawItem`,
`drawInto`), `prepareTorch`, the loadout writes in `enforce.mjs` inside the
per-actor queue, and the attack throw. The attack's wait is a `ready()` a
contributor to `lib/patches/attack-throw.mjs` may declare, awaited by the one
existing `makeAttackThrow` wrapper before the throw is built; equipment declares
`rowsSettled`. No second wrapper was added, so the one owner of that core method
stays the lib seam.

**Rejected.** A guard in each reader (`classifyWeapon`, `isWeaponProficient`)
that answers "wait" for the load window: they are synchronous and read at every
render, and a third answer between "stated" and "not imported" is what the
undecided rule exists to avoid. A second wrapper on the attack path from
equipment: one owner per wrapped core method. An unbounded wait: a library that
never loads would freeze every draw and attack.

**What it cost.** A draw or an attack in the load window answers a few seconds
late instead of early and wrong. Core's own equip toggle in `veto` mode is
judged in `preUpdateItem`, which cannot wait, and a sheet opened in the window
shows the early answers until it redraws.

## 2026-11-13 — The lock is the Judge's, and a player has to beat it

**Ruled.** Three owner controls each open a locked container in one click: Unlock (there is no key item to check, so it is a free pass), Empty and Unmake. Only the GM gets them, because at a table the Judge is who opens it for you, including when the character legitimately holds the key. A player facing a locked container gets the two controls that have to beat it, pick and bash, both of which roll, and each is offered only when the character has the proficiency. Locking is always available, since shutting your own box is not a bypass.
**Rejected.** Giving every owner all three controls: the lock would be the whole feature undone, since nobody would pick a lock they can click off.

## 2026-11-13 — Light controls never wait on a formation

**Ruled.** A character in no formation keeps its lights as a flag on its own actor, written directly with no GM and no declaration card, and the Light / Douse / Shutter controls render without a party record. A character in a formation declares through `requestPartyAction`, which relays to the active GM's client; a GM calls straight through, which keeps a Judge lighting a lamp out of the public "declared" card.
**Rejected.** Requiring a party record to hold the state (a formation of one): a lone character had no way to light anything and the lantern showed no control.
*Cost:* the lone path has no burn-down, since outside a formation there is no dungeon-turn clock.

## 2026-11-13 — A named item keeps no renown or experience track of its own

**Ruled.** Unlocking a named item's bonuses is tied to levels of experience earned while wielding it (an unlock per level gained), never to any renown or XP track the item holds itself.
**Rejected.** A renown or XP track on the item.

## 2026-11-13 — Two shield effects stay with the Judge

**Ruled.** The overlay does not automate the loss of a shield's benefit while the wielder is vulnerable, which needs per-attack context the system has no model for, nor the mounted choice between protecting self and protecting the mount, which is a player's choice each round and not a derivable fact. Both are surfaced in the item descriptions for the Judge.

## 2026-11-13 — A spell book is a recognised item class and holds its spells as data

**Ruled.** The Spell Book the importer generates from the equipment list is the spell book, and only it carries the page and value model; the model is not a property switched on for arbitrary gear. Recognition is by name or by an already-stored spell list, so a configured book keeps its identity if renamed. Its spells are stored as data on the book (name and level), not as links to the finder's spell documents, so a looted book's formulae travel with it and appear on nobody's Spells tab until learned.
**Rejected.** Linking the finder's own spell documents.

## 2026-11-13 — Uninstall strips what the module wrote, and reverts stat layers only on request

**Ruled.** The cleanup deletes the managed Equipment Loadout effect, because with the module off it would keep applying stale modifiers invisibly, the one leftover that actively corrupts play. It always reveals disguised items first, because the mask writes a fake identity into core fields and stripping the flag first would make it permanent. It reverts the masterwork, scavenged and item-loss stat layers to the pristine snapshot only when asked (`revertLayers`, off by default), because most tables want to keep what the fiction earned; unlocked named-item rungs stay in core fields either way as earned state. It then removes every `flags.acks-extras.*` on actors and items.

## 2026-11-14 — A named item's bonus categories are procedure, and their labels name fields

**Ruled.** The five categories a named item's points go to (`overlays/named.mjs` `NAMED_CATEGORIES`, JJ p. 399) stay in source: each is a modifier the overlay applies to a field core owns, and the code that applies it is keyed by it, so the set is which modifiers exist and not a table of options read off a page. A label names its field and carries no size; the count beside it is the ladder the Judge set, one point a rung. The building session's call with the owner away. A reversal registers the categories as an imported table and has `toItemUpdates` read which field each one writes.
**Rejected.** A label that states the size of a point, which is the page's figure in a string.

## 2026-11-17 — A weapon with no damage formula stays blank, and its first attack asks — SUPERSEDED IN PART 2026-11-25

**Ruled** (owner, answering the phase-3 assessment's note that a named weapon
with no damage formula had a die written for it): "A no default should stay
blank and prompt (and save response) for damage formula on first roll." An
example: a named weapon whose formula is blank, with one damage rung unlocked,
keeps a blank damage field; the first attack with it asks for the formula, a
`1d8` typed there is saved as the weapon's base, and the field then reads
`1d8+1`. The next attack asks nothing.

**Decided.** Every invented die for a missing formula is removed: the named
overlay's captured base and its applied bonuses, a scavenged condition's
penalty, the property layers' flat delta over a blank snapshot, the Follower
Card's new attack and a template package's weapon with no stated die. The ask
is a `prepare(ctx)` a contributor to `lib/patches/attack-throw.mjs` may
declare, awaited by the one existing `makeAttackThrow` wrapper before the
throw is built, as `ready()` was (2026-11-13, "The draw and the attack wait for
the weapon rows"); the equipment feature declares it in `damage-prompt.mjs`.
The prompt comes before the throw, not at the hit, because the system parses
the formula inside its own builder through the synchronous `getDamageFormula`,
which cannot wait for an answer. It answers to no setting.

**Rejected.** A wrapper of `getDamageFormula` that prompts: it is synchronous,
and the lib's seam already owns it. A second wrapper of `makeAttackThrow`
from equipment: one owner per wrapped core method. Asking only on a hit: the
hit is decided inside the system's builder, after the point a prompt can be
awaited. Keeping a die as a fallback with a warning: the ruling's words.

**What it cost.** An attack with a blank weapon asks before the throw, so a
miss also asks once. An attack begun from the system's own dialog with no
weapon named (the Rolls tab's bare melee and missile rows) picks its weapon
inside the system's builder, past the seam, and a blank weapon chosen there
still rolls no damage, unasked. A named weapon that took the old die keeps
it: the stored base cannot be told from a stated one.

## 2026-11-19 — A weapon is silver when core says so

Supersedes in part "Silver is a quality, not a material (2026-08-06)": that a
weapon's silver "rides its own flag", and that the weapon table's row and the
item's name decide it when the flag is silent (and the flag's `false` denies a
name). It also supersedes in part "2026-11-17 — Silver's answer reads the
weapon's own extraordinary mark": that `dealsExtraordinaryDamage` stands.

New evidence, since the 2026-11-17 entry is under a week old: lib's damage
stage (lib DECISIONS, "2026-11-16 — Damage against defenses is one lib stage")
reads core's `system.special.silver`, not the flag, so a weapon could be silver
to `isSilvered` and not to the stage that decides a hit. And
`dealsExtraordinaryDamage` has no runtime caller (a grep finds it only in
`api.mjs` and its own test) and contradicts that stage's rule that silver
counts as extraordinary only against a band with `silverFlaw`.

**Ruled** (architect, accepted by the owner). For a weapon, core's
`system.special.silver` is the truth, read through lib `silverOf`.
`isSilvered(weapon)` is `silverOf` and consults neither the flag, the row nor
the name. The module's `silvered` flag means "plating bought", which is what
the price layer reads, and never answers "is it silver" for a weapon. The
Construction tab's Silver control keeps its three options: *Silvered* sets the
flag and `system.special.silver` true; *Not silvered* writes the system's field
and the flag false (the price layer keys on `true` alone); *Auto* unsets the flag and leaves the system's field
alone, so its "Auto (…)" label reports that field. Ammunition has no core
silver field and its stack is picked in the post-attack hook, so it keeps the
flag, then the row, then the name. `dealsExtraordinaryDamage` is retired.

**Rejected.** Reading the flag in lib's stage: lib reads core's fields and
nothing of Equipment's (lib DECISIONS 2026-11-16). Keeping the name fallback
for weapons: a weapon called silver that core does not mark deals mundane
damage to a silver-flawed monster, and the sheet would say otherwise.

**What it cost.** A weapon plated before this change keeps its price but is not
silver until Silvered is picked again; it was never silver to lib's stage. The
owner rules no migration ("no tools for previous-version data"). A weapon
named for silver is not silver until the field is ticked (the sheet's Silver
quality chip or the control). The importer lights a system special for every
word of a weapon row's Special cell that names one (`settleQualities`), so an
imported weapon whose printed cell says silver carries the field; whether a
given row's cell does is the Judge's book, not read here. A weapon whose chip is cleared
while the plating flag is still true keeps the plating price, and its picker
reads Auto (Not silvered), since the picker shows a stored pick only while the
field agrees with it (`silverChoiceOf`).


## 2026-11-24 — Equipping a stack takes one from it

The equip write is the seam: `preUpdateItem` vetoes first, then a row of two or
more that core can equip is divided (`divertsEquip`, `takeOneToEquip` in
`item-sheet/stack.mjs`), then an unstow applies. `foldOnUnequip` and
`recoverThrown` fold a returned row into its resting one. The ruling, its
rejected alternatives and its cost are in `docs/lib/DECISIONS.md`, "A weapon or
a suit of armour folds into a stack, and equipping takes one from it". The
handlers live in `enforce.mjs` (`onPreUpdateEquip`, `foldOnUnequip`) and
`module.mjs` only registers them, so the handler order is testable. `placement.mjs`
offers no take-out for a core-equippable item.

## 2026-11-24 — Armour class is the system's sum

Supersedes "A helmet never replaces the suit (2026-11-10)" (archived in
`DECISIONS-through-v11.14.5.md`; it carries no row in "In force"). **New
evidence:** `acks` 14.2.0's `computeAC` adds the AC of every equipped armour
not typed "shield" to the base and the AC of every equipped shield to the
shield figure. The 14.1.0 `computeAC` the ruling answered took its base from
the last such armour and its shield from the last shield.

**Ruled.** The armour part of AC is the system's alone: the loadout effect
writes no armour-base change to `system.ac.mod`, and the Loadout no longer
names `coreArmorBase` or `armorBase`. The shield cut follows what the system
now adds: the variant cut (`shieldACCorrection`) cancels the AC of each
equipped shield that `grantsOrdinaryAC` says grants nothing, the style cut
cancels the AC of every equipped shield while `shieldStyled` is false, and the
effect still takes the deeper of the two, once. With one shield the figure is
unchanged. The character sheet's AC tooltip lists every equipped armour not
typed "shield", each with its own figure, and their total (`summedArmour`).

**Rejected.** Keeping the base correction: on 14.2.0 the system already sums a
suit and a helmet, so the correction counts the suit's AC a second time. A
rule about a second shield (only the best one counts, or none): the module
cancels only what its two existing rules already say grants nothing, and
nothing here adds a third.

**What it cost.** A helmet stating an AC adds it to the suit's whichever went
on first, as before, and now by the system's own sum. A world that stays on
14.1.0 reads the old base and would see the helmet stand in for the suit; the
module's minimum is 14.2.0. Every shield worn beyond the first is now cut
(or kept) by the same two rules rather than ignored.


## 2026-11-24 — A write during a divide or a fold waits for it

**Ruled.** The equip hook returns false at once and the divide lands 15 to 90 ms
later, so a script that equips a stack and immediately unequips it wrote
`system.equipped: false` against a row still reading resting. Foundry runs the
preUpdate hooks before it diffs, and an empty diff is skipped, so the unequip was
dropped and the row ended drawn; a mixed write (`markThrown`, `sheatheItem`)
landed its flag and lost the unequip. The reverse, an unequip followed by an
equip while the fold is still joining the rest back, sent an equip the hook did
not divert (the count was 1), and the fold then raised the drawn row to the whole
stack. The ruling that weapons and armour fold into stacks and that equipping
takes one from the stack stands; this makes it hold for scripts and macros. A
draw in flight holds a write that unequips the row, a fold in flight holds a
write that equips it, and the held write is issued again, whole, when the
holder's queue has finished the work (`holdWhile`, `holdsWrite`, `afterTurn` in
`item-sheet/stack.mjs`; the first branch of `onPreUpdateEquip`). The direction
split is the rule: holding every equip write would hold the divide's own write,
refuse the reduce and lose the rest of the stack.

**Rejected.** Mutating `changes` inside the hook to carry the held write: the rest
row cannot be awaited there, which breaks "made before reduced" in `stack.mjs`.
An awaited wrap of the document's `_preUpdate`: a new wrap of a core method, and
a double click inside the create would divide twice.

**What it cost.** `await item.update()` on a held write still resolves
`undefined` before the write lands, as it already did for the diverted equip; a
caller that must read the result awaits the holder's turn, not the update. The
count is per client, so two seats equipping one stack inside the window could
each divide it; that is registered separately. The re-issue is a plain update and
drops the held write's options.

## 2026-11-25 — The strike and a spell carrier are never asked for a formula — SUPERSEDED IN PART 2026-11-25

The strike's half is superseded by "2026-11-25 — An unarmed strike with no die
asks, and a Judge can keep the answer" and, for the carrier, by "2026-11-25 —
A spell attack with no damage die asks, and the die is kept per copy"
(`docs/magic/DECISIONS.md`).

Supersedes in part "2026-11-17 — A weapon with no damage formula stays blank,
and its first attack asks": its reading that every blank weapon asks. Two
rulings meet here. "2026-11-11 — Capacities, finesse sizes and the unarmed die
are read, not shipped" (archived in `DECISIONS-through-v11.14.5.md`, "In
force") says a blank unarmed die means an attack throw and no damage roll. The
2026-11-17 entry says a blank weapon asks, and saves the answer.

**Ruled** (the release orchestrator, on the owner's delegation, pending the
owner). The prompt is for a weapon that can keep the answer. The unarmed strike
(`actions.mjs` `rollUnarmed`) and a spell carrier (lib `spellCarrier`) are
unsaved weapons built for each throw, so an answer typed for one is kept in
memory only and the next throw asks again. They are never asked and take the
2026-11-11 reading: a blank formula is an attack throw with no damage roll. Each
is told by identity (`isUnarmedStrike`, `isSpellCarrier`), not by a missing id,
since an unsaved weapon from anywhere else still takes an answer in memory. An
example for each: a character with no unarmed die imported presses Unarmed
Strike and the throw is made with no prompt; a stored club with no formula still
asks once, saves what is typed and asks no more.

**New evidence.** The live walk was held from 2026-11-18 on the strike's own
prompt: the strike cannot save the answer, so it asked on every throw, and
`skipDialog` does not skip it. The 2026-11-17 entry was written for a weapon that
can save the answer.

**What it cost.** A Judge who wants the strike to roll damage imports the die;
there is no prompt to type one into. A spell carrier whose row states no roll
makes an attack throw and no damage, as before the prompt existed.

## 2026-11-25 — An unarmed strike with no die asks, and a Judge can keep the answer — SUPERSEDED IN PART 2026-11-25

Superseded in part by "2026-11-25 — An unarmed strike's die is kept on the character or the world, and the Judge is offered it". **Ruled** (owner, on being asked whether an unarmed strike with a blank die
should make an attack throw and no damage roll, with no formula prompt):
"prompt (and offer to save) damage if none is specified when rolling". An
example: a world with no unarmed die imported, a character presses Unarmed
Strike under Rolls tab → Attack, and a window asks for the die; `1d3` typed
there is the damage of that throw.

**New evidence.** The earlier entry, written the same day and under a day old,
was a ruling of the release orchestrator pending the owner. The owner's answer
reverses it, and it names the save the entry said the strike could not have:
"offer to save".

**Decided.**

- The strike with no die opens its own window (`unarmed-prompt.mjs`), built
  with the `DialogV2` constructor so a refusal stays on the window: a typed
  answer is read by the one test the unarmed die's reader uses (`NdM` only,
  `attack-mods.mjs` `asUnarmedDie`), since a die the table would read back as
  not imported would be asked again on every press. Closing the window cancels
  the attack.
- Where the seat has Foundry's `SETTINGS_MODIFY` permission, the window also
  offers an unticked "Save as this world's unarmed die". Ticked, the die is
  written as the world's override of the equipment document's `unarmedStrike`
  table (`{damage}`), the layer the Ruledata Browser shows and clears (`Settings
  tab → Game Settings → ACKS II — Extras → Imported Rules Tables → Open
  Ruledata Browser`); the next press finds a die and asks nothing. Unticked, the
  die applies to that throw only.
- A seat without the permission is given the field and Attack, and a line that
  says nothing can be saved there; its die applies to that throw and the next
  press asks again.
- `setOverride` and `clearOverride` (`location/table-store.mjs`) test
  `game.user.can("SETTINGS_MODIFY")` and no longer `isGM`, which is the owner's
  standing rule that a gate reads Foundry's own permission and invents none.
  The Ruledata Browser's menu is registered restricted and stays Judge-only.
  The `ruledata-import` contract gains an additive `setOverride` (v1.5), so
  equipment writes through the service and not through the location feature's
  file.
- A spell carrier with a blank die, and a stored weapon, were unchanged here:
  the carrier asked nothing (superseded, `docs/magic/DECISIONS.md`, 2026-11-25);
  a stored weapon asks once and saves the answer on the item.

**Rejected.** Saving into a world flag or a setting of equipment's own: a
second place for the die, with no surface to show or clear it. Asking a seat
that cannot save to ask a Judge: a prompt with no way to answer it at the table.

**What it cost.** The strike's die has two writers, an import and a Judge's
override, as every imported table already does; the override wins and the
Ruledata Browser is where it is undone. A Judge who ticks the box on a typo has
to clear it there.

## 2026-11-25 — An unarmed strike's die is kept on the character or the world, and the Judge is offered it

Supersedes in part "2026-11-25 — An unarmed strike with no die asks, and a
Judge can keep the answer", written the same day: its seat without world-settings
permission, which was given the field and Attack alone, is now given a way to
keep the die when it owns the character.

**Ruled** (owner, on the design board's card, in free text): "offer to save for
character (fwd offer to judge to save for all instances), offer to save for all
instances to judge by default". An example: a Player who owns Hero presses
Unarmed Strike with no die set, types `[dice]`, ticks "Save as this character's
unarmed die", and attacks. Hero rolls it from then on and is not asked again; the
Judge is whispered a card and may press one control to make it the world's die.

**New evidence.** The earlier entry rested on the hub's reading that a seat
without world-settings permission has nowhere to write. The owner's words name
the character as that place, and the seat's own right to edit the actor as what
writes it.

**Decided.**

- A seat with world-settings permission is offered one box, "Save as this world's
  unarmed die", as before. It is offered by default and is unticked.
- A seat without it that Foundry lets update the actor (`canUserModify`, which
  an owner passes) is offered "Save as this character's unarmed die". Ticked,
  the die is the character's flag `flags["acks-extras"].unarmedDie`, written
  by Foundry's own ownership of the actor, and the strike reads it first.
- That save sends one whispered card to every seat that may modify world
  settings, naming the character and the die, with one control, "Save as this
  world's unarmed die", which writes the same override the Judge's box writes.
  Ignoring it changes nothing, so there is no decline control. The card holds no
  state: it reads the world when it is drawn, so a die the world already holds,
  this die or another, replaces the control with a line, and a seat that cannot
  write the world sees that the Judge was offered it and no control.
- The strike rolls the character's die, else the world's (a Judge's override,
  then the import), else asks. On the Rolls tab's Unarmed Strike row the line
  leads with the die; a character's own carries the "set by hand" mark and a
  tooltip naming what it stands in for and the page, and its owner a control that
  clears it, after which the strike reads the world's die.
- A seat with neither right is given the field and Attack alone, as before.
- The die is still one `NdM` die, refused on the window, and closing the window
  cancels the attack and sends no card.

**Rejected.** A second box in the Judge's window for the character: the Judge
who wants it on one character attacks once and the character's owner or the
Judge keeps it from that character's own window. A decline control on the card.
Writing the character's die from the card's press: the Judge's press is for the
world only.

**What it cost.** The die has a third home, the character, which wins over the
world's override on that character alone, so a Judge who sets the world's die
afterward finds characters that keep their own. The Judge sees each by its mark
on that character's sheet and has no list of them.
