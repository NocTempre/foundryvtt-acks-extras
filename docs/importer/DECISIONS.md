## 2026-11-13 — Book repair reaches a book's own rows and vehicles (T-0458)

**Reported.** The owner's report: Rebuild on a bestiary left a beastman
template as a card the importer no longer writes, and the owner's ruling of
2026-11-10 put it where it belongs: it is an importer issue, and no
compatibility layer holds the old card.
Book Rebuild and book Repair are one function (`cookbookReimportBook`,
`repairBook`), and it never wrote the Monsters kind, nor the vehicles, nor the
one journal and one roll table the rules and the Judge's book print. A Judge
whose library's beastman template lacks the Kit axis presses Rebuild on
the bestiary and gets the current-shape template under the same id; the
sidebar copy is untouched.

**New evidence, superseding in part "A book is a reimport unit too"
(2026-09-16) and the clause of "An adventure book is a reimport unit"
(2026-10-28) that said `cookbookReimportBook` takes shelf Items alone.** Both
reasons for the limit are gone. The 2026-09-16 book run deleted first, and an
actor had no in-place writer; "Every kind gets an in-place write" (2026-11-04)
gave every kind one, and "One repair, in place" (2026-11-11) made every
rebuild control write in place and delete nothing. `repairBook` was never
widened to match. The owner's report is the case that shows it.

**Ruled.**

- **A book repair writes a book's own rows.** On a book with a cookbook of its
  own that is no Judge's book, `repairBook` runs the book's own steps after its
  shelf runs, under the same tally (`runAdventureBookSteps` with `items: false`,
  since the shelf run wrote the items, and `adventure: false`). Its confirm
  names them (`ui.repairMergedBookOwn`). A Judge's book keeps
  `cookbookReimportAdventure` alone, so no row is written twice.
- **The vehicles are a book's.** The vehicle run joins the book scope
  (`viaBook`) and `repairBook` takes a source that names no shelf whole
  (`!src.shelves`, which retires `bookOwn`). The census counts a document by the
  entry its claim names or sits beneath (`ancestorsOf`), so a vehicle's rows and
  a merchandise row are counted as written, where the merchandise rows were
  counted as left.
- **`runSetFor` names a book's own rows as one run on every book**; the
  `isAdventureBook` condition goes.

**Rejected:** the own rows on a Judge's book (the adventure repair already
walks them, twice over); re-reading the rules tables in a book repair
(Repair everything already does); Import everything writing over held
documents (a reversal of its contract, so a new behaviour); driving
`repairBook` from `cookbookRunSet` (nothing calls the derivation yet).

*Cost:* a bestiary repair refills every held creature of it, minutes where a
shelf repair took seconds. Repair everything's book rows gain the bestiary's,
the rules' and the Judge's book's own-rows lines.

## 2026-11-13 — A bulk import reads each page once (T-0353)

**Ruled by the owner** (T-0353, "Import takes forever which might be driving
bugs"): "in this release; measured first". The phase ruling is "Fixes in, new
features out", so this is the two page caches and nothing that changes what an
import writes.

**What was measured, offline, against the real books.** Two steps of Import
Everything re-extract pages the run has already read. The rules-tables step
(`importTables`, Settings tab → Game Settings → ACKS II — Extras → Manage
imports) scans pages outward from each recipe's guess, and recipes of one book
overlap: 292 recipes made 727 `getTextContent` calls over 194 distinct pages,
188 of them read more than once and one sixteen times. The abilities update
pass (`cookbookUpdateAbilities`) ran `executeEntry` once per definition with a
fresh cache each time: 523 definitions made 561 extractions over 83 pages. The
import half of the abilities pass already shared a per-run cache
(`runPageCache`); the update half did not.

**Ruled.** `importTables` holds one page reader for the call, a map per
document from page to the pending read, dropped when the read rejects so the
next recipe retries. `cookbookUpdateAbilities` holds a `runPageCache` for the
run and gives `executeEntry` the one for the definition's book. Both caches end
with the call; the next call reads the books afresh. The ladder expansion in
the update pass keeps its own reads, because a ladder spec can read another
book's entry than the ability's. The documents written are unchanged: the
tables step hands `importDoc` the same 34 documents byte for byte (sha256 equal
before and after), and the abilities probe's `executeEntry` output is equal with
and without a shared cache.

**This is not the 2026-08-24 ruling reversed.** "Writes are batched, because a
write costs what the shelf already holds" rejected page extraction as the cost
of the ability IMPORT on a live world, finding a shared cache "changed nothing
measurable" there, and kept the cache. That measurement was a definition's parse
and the write that followed it. It never timed these two steps' extraction, and
offline an extraction costs 30 to 35 ms a page, which 561 reads turn into some

## 2026-11-16 — A repair holds a spell's edited and deleted rows, and its edited `values`

Supersedes the cost line of 2026-11-15, "A repair tells a spell's rows apart by
`origin`", and the spell-rows part of the spell-effects plan's ruling 3. The
owner's words are the plan's: "Spells want their proper effects, damage/effects
should apply with correct amount and type", and "automation with transparency
is the design principle".

**New evidence.** Session 1a walked the repair live: an edited register row plus
a repair left two register rows beside each other, four in all on one spell; a deleted register row came back; and a `values` leaf a Judge had
typed was overwritten. The first ruling accepted the doubled row as a cost
while a row was only a listing. The cast slices make rows executable, so a doubled
damage row applies twice and a deleted one returns to hit a target the Judge
removed it for.

**Ruled:** every register effects spec carries an authored `key`
(`/^[a-z][A-Za-z0-9]*$/`, unique per entry, a reversed twin's distinct), the
lint requires it, and a row a Judge adds is keyed `_` plus a random id.

- *An edited row.* A stored row with no `origin` whose key is a fresh register
  key stands in for the fresh row, which is not added. Where it no longer
  covers it the repair lists a held edit, default keep; taking it puts the
  fresh row in its place.
- *A deleted row.* The row editor's delete passes the removed row to the spell
  store, which adds a register key to `SpellExtras.retired` in the same
  update. A repair skips a retired key and lists a held edit; taking it writes
  the row and clears the key.
- *`values`.* `bindSpell` records each leaf its fragments wrote in
  `cookbook.read.spell`; a stored leaf equal to the stamp takes the page, one
  differing from both stamp and page is a held edit, one with no stamp takes
  the page.
- *Forced.* `force` makes the page win everywhere except on a `_` row.

The held edits go through `decidedPolicy` and the merged repair's choice
dialog, as the prose guard's do; a row reads as its one-line description on
both sides.

**Rejected:** a `supersedes` field on the row (the register would name rows it
no longer writes); a key minted at compile from the row's position (reordering
the recipe would rename every row in every world); standing in silently (an
edit the page has since moved past would never be offered).

*Cost:* every repair lists each edit that still differs, until the Judge takes
it or the edit is undone. A world imported before this has stamped rows with no
key: its first repair replaces them from the build, and an edited row of that
age, having no key, stays and is joined by the fresh row once. A Judge's edit
to a stat-block field outside `values` (range, duration) is still overwritten:
only `values` leaves carry a stamp.

## 2026-11-16 — A zone's cells are core's grid shape — SUPERSEDED IN PART 2026-11-16

  that one book's list hops and the other's does not without the engine reading a

- **A book's list is placed, or the shared list stands.** A list is placed when its
  bands tile and, for a hopping list, every leaf band's hop resolves to an id under

  belongs to the id, not the standing list, so a Journal type row still reaches a
  list the Tome replaced and a Tome type row reaches a list the Journal still
  holds.

## 2026-11-18 — The cookbook drift check measures against where the work meets main

The owner was asked to choose between two options for the drift check. One
skips the recompile when nothing it reads differs from the gated base. The
other moves the full recompile to the release check and the nightly run. The
owner answered: "A: skip vs gated base". This supersedes the committed stamp
of "The cookbook drift check recompiles only when its inputs moved"
(2026-11-17). The new evidence comes from the day the stamp was in use:

- **The skip held on 1 of the 16 gates between the stamp's landing and 03:52
  on 2026-11-18.** The other 15 recompiled in full, at 721 to 1124 s of
  validate each. A gate's full pass rewrites the stamp in its scratch clone,
  and the clone is thrown away. So `main`'s stamp went stale with each input
  commit until a session committed one by hand, which two stamp-only commits
  did (7d8580bf, b9dbfdb7).
- **Every importer change rewrites the same file.** Two topics that touch
  compile inputs therefore conflict on the stamp when they land. On
  2026-11-18, a topic's fast-forward waited on another session's uncommitted
  stamp.

The ruling:

- **The base is `git merge-base HEAD main`.** That is `main`'s tip in
  `main`'s own tree, the change's base in a commit tool's clone, and where a
  topic meets `main` in its own checkout and in the clone that gates its
  landing. `origin/main` stands in where the local `main` is missing. The
  recompile runs when any path that differs from the base is one the compile
  reads, whether tracked or untracked (ignored paths do not count).
  Otherwise the check prints one line naming the base and passes. With no
  base, or any git failure, the full check runs. What counts is the header of
  `tools/importer/cookbook-inputs.mjs`.
- **No stamp is committed.** `cookbook-stamp.json` and `cookbook-stamp.mjs`
  are removed. `cookbook-inputs.mjs` keeps the import walk and the register
  selection, and matches paths by rule, so a removed file counts. The walk
  and `ACKS_COOKBOOK_DRIFT_FULL=1` stand as ruled on 2026-11-17.
- **Rejected: B, the recompile only at the release check and the nightly
  run.** A drift would be caught after the session that caused it has moved
  on, and traced back by hand.
- **Rejected: keeping the stamp beside the base rule.** It keeps the
  contended file and its commit chore, for no skip that the base rule misses.

*Cost:*

- **The skip trusts that what `main` holds passed its own gate.** A commit
  that reaches `main` without the full check is not checked again until a
  later change touches a compile input. Three routes do this: a change
  committed with `"gate": []` that touched an input, a carried base (the
  carry stages leave validate out), and a commit made around the commit tool.
  `postgate` on a commit already on `main` measures the commit against itself
  and skips. Where that matters, the gate sets `ACKS_COOKBOOK_DRIFT_FULL=1`.
  The stamp corrected such a commit at the next mismatch; the base rule does
  not.
- **Two inputs the stamp hashed do not show in a diff.**
  - A reference PDF's size: a PDF replaced under the name `reference-lib.mjs`
    gives it goes unseen, while a new printing changes the name, which is a
    diff.
  - A package's installed version: `package-lock.json` stands in for it.
- **A peer's edits count too.** Every differing path counts, including a
  peer's uncommitted edit. So a validate in `main`'s shared tree recompiles
  while any session holds an uncommitted edit to a compile input, as it did
  under the stamp.
- **The suite is slow.** It builds real git repositories, about 110 git
  processes: 20 to 30 seconds on this machine.
