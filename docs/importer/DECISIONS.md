## 2026-11-13 — Book repair reaches a book's own rows and vehicles (T-0458)

**Reported.** The owner's report: Rebuild on a bestiary left a beastman
template as a card the importer no longer writes, and the owner's ruling of
2026-11-10 put it where it belongs: it is an importer issue, and no
compatibility layer holds the old card.
Book Rebuild and book Repair are one function (`cookbookReimportBook`,
`repairBook`), and it never wrote the Monsters kind, nor the vehicles, nor the
one journal and one roll table the rules and the Judge's book print. A Judge
whose library's beastman template lacks the Kit axis presses Rebuild on
the bestiary and gets the current-shape template under the same id; the
sidebar copy is untouched.

**New evidence, superseding in part "A book is a reimport unit too"
(2026-09-16) and the clause of "An adventure book is a reimport unit"
(2026-10-28) that said `cookbookReimportBook` takes shelf Items alone.** Both
reasons for the limit are gone. The 2026-09-16 book run deleted first, and an
actor had no in-place writer; "Every kind gets an in-place write" (2026-11-04)
gave every kind one, and "One repair, in place" (2026-11-11) made every
rebuild control write in place and delete nothing. `repairBook` was never
widened to match. The owner's report is the case that shows it.

**Ruled.**

- **A book repair writes a book's own rows.** On a book with a cookbook of its
  own that is no Judge's book, `repairBook` runs the book's own steps after its
  shelf runs, under the same tally (`runAdventureBookSteps` with `items: false`,
  since the shelf run wrote the items, and `adventure: false`). Its confirm
  names them (`ui.repairMergedBookOwn`). A Judge's book keeps
  `cookbookReimportAdventure` alone, so no row is written twice.
- **The vehicles are a book's.** The vehicle run joins the book scope
  (`viaBook`) and `repairBook` takes a source that names no shelf whole
  (`!src.shelves`, which retires `bookOwn`). The census counts a document by the
  entry its claim names or sits beneath (`ancestorsOf`), so a vehicle's rows and
  a merchandise row are counted as written, where the merchandise rows were
  counted as left.
- **`runSetFor` names a book's own rows as one run on every book**; the
  `isAdventureBook` condition goes.

**Rejected:** the own rows on a Judge's book (the adventure repair already
walks them, twice over); re-reading the rules tables in a book repair
(Repair everything already does); Import everything writing over held
documents (a reversal of its contract, so a new behaviour); driving
`repairBook` from `cookbookRunSet` (nothing calls the derivation yet).

*Cost:* a bestiary repair refills every held creature of it, minutes where a
shelf repair took seconds. Repair everything's book rows gain the bestiary's,
the rules' and the Judge's book's own-rows lines.

## 2026-11-13 — A bulk import reads each page once (T-0353)

**Ruled by the owner** (T-0353, "Import takes forever which might be driving
bugs"): "in this release; measured first". The phase ruling is "Fixes in, new
features out", so this is the two page caches and nothing that changes what an
import writes.

**What was measured, offline, against the real books.** Two steps of Import
Everything re-extract pages the run has already read. The rules-tables step
(`importTables`, Settings tab → Game Settings → ACKS II — Extras → Manage
imports) scans pages outward from each recipe's guess, and recipes of one book
overlap: 292 recipes made 727 `getTextContent` calls over 194 distinct pages,
188 of them read more than once and one sixteen times. The abilities update
pass (`cookbookUpdateAbilities`) ran `executeEntry` once per definition with a
fresh cache each time: 523 definitions made 561 extractions over 83 pages. The
import half of the abilities pass already shared a per-run cache
(`runPageCache`); the update half did not.

**Ruled.** `importTables` holds one page reader for the call, a map per
document from page to the pending read, dropped when the read rejects so the
next recipe retries. `cookbookUpdateAbilities` holds a `runPageCache` for the
run and gives `executeEntry` the one for the definition's book. Both caches end
with the call; the next call reads the books afresh. The ladder expansion in
the update pass keeps its own reads, because a ladder spec can read another
book's entry than the ability's. The documents written are unchanged: the
tables step hands `importDoc` the same 34 documents byte for byte (sha256 equal
before and after), and the abilities probe's `executeEntry` output is equal with
and without a shared cache.

**This is not the 2026-08-24 ruling reversed.** "Writes are batched, because a
write costs what the shelf already holds" rejected page extraction as the cost
of the ability IMPORT on a live world, finding a shared cache "changed nothing
measurable" there, and kept the cache. That measurement was a definition's parse
and the write that followed it. It never timed these two steps' extraction, and
offline an extraction costs 30 to 35 ms a page, which 561 reads turn into some
19 s and 727 into some 22 s on an idle machine (a loaded one measured 65–144 s
and 71–109 s). Whether the live saving is that large is open: live figures to
follow.

## 2026-11-13 — The rules tables are read first and applied after the classes

**Ruled by the owner.** Two rulings, verbatim:

- Plan §21.0f: "I am okay with leaving a duplicate import source unbuilt for

  unload from book, phase 2 organize in foundry. I suspect a lot of wonkiness

- Plan §36.6, the options A, B and C offered, answered: "A: tables-first slice"

**Ruled.** Import Everything reads the rules tables first and applies them
after the classes. The read is `stepTables`: the page read, then the store's
assembly of the builder and travel tables, with its report kept in the chain's
run object. The apply is `stepTablesApply`, after `stepClasses` and before
template packages, and it writes only the documents that report names: races,
class builds, skill armour-limit rows and languages. Then it syncs race
tongues. The split falls there because class pricing needs the assembled
builder tables, and races and builds need the abilities and classes the chain
has just made. A chain never applies a table it did not read in the same run.

first part runs, and applies them once in `finish`, after the last pass and

repair rewrites the class's whole system, so a second pass that re-ran the

for the Yes because the asking pass writes nothing and a No must leave the
world as it was, and the read writes the table store and its materialized
tables.

classes the run made, and fills only a race whose list is empty. It runs when
an apply runs, which happens only when the read named the builder or language
document. Borrowing for a new class takes its lenders from every held class;
the borrowers stay the classes the run wrote, because a borrow is not
idempotent: each one gives a slot back.

A repair's read memo (`holdingReads`, `read.mjs`) is opened by `runMerged` and
lasts for that one merged repair, both passes, the finish and the Judge's
choice dialog. It is gone when the repair ends. Import runs open none. It holds
executed nodes, never pages, and each read gets a copy.

This is a reordering and a read seam. It is not the two-phase structure the
owner asked for in §21.0f, which heads the next roadmap.

call. Class pricing reads the builder budget, which exists only after the

(2026-11-11; the two passes are unchanged). "Book repair reaches a book's own

"A bulk import reads each page once (T-0353)" (2026-11-13; the call caches are
unchanged, and the memo above is a separate store).

## 2026-11-13 — A picture's text is read by an `ocr` field op over a per-page recipe, once per opened book — SUPERSEDED IN PART 2026-11-13

writes nothing and posts no card; the sheet's Roll is disabled on such a place
and says on the surface that a lair rolls from its world copy. A world copy
made by the importer (`worldCopySource`) keeps the monster the lair is of and
nothing the shelf place rolled: no `lair.group`, no `lair.noted`, and no
roster row for that group (`lairForCopy`). This narrows "rolls once" to once
per world lair.

**Rejected:** one group shared by the two documents, linked from the shelf
place by uuid. It would make the shelf place carry a world document's uuid, a
reference the shelf cannot resolve in another world or after a restore, and
leave every roll that arrives on the copy writing to a compendium document.

*Cost:* a lair with no Scene, which the shelf alone holds, is rolled only after
its place is dragged out of the compendium into the world; the Roll button on
the shelf place is a dead end that says so. A world copy dragged out by core
rather than made by the importer carries the shelf place's flag as it stands,
which is the monster alone for any place that rolled after this entry.

## 2026-11-14 — A made L&E stat line is paired where its figures match the MM row

The owner, on the rank-and-file stat lines that may duplicate an MM row: "Pair
after compare (Recommended)". This supersedes in part the rejected "a pair for a
label qualified by a role, age or size" of "A lair links to its monster…"
(2026-11-13): the new evidence is that answer and the comparison itself, which
shows which of those lines print the row's own figures.

**Ruled** (the owner's answer is the quotation; the definition of a match is
the design's; the normalisations and the treatment of an unread figure are the
implementing session's, open to the owner's ruling):
`tools/importer/compare-lines.mjs` reads the Judge's L&E and MM copies
through the shipping executor and compares every made stat line with the MM rows
its label may stand for (a row sharing a creature word with the label, the row
the lair's `meta.of` names, the row the conversion table renames the label to).
**A match** is every gating figure equal at every occurrence of the label: armor
class, hit dice (dice and modifier), attacks with their damage, save (class and
level) and morale. Movement, experience and alignment are reported and gate
nothing. Notation is normalised, and only that: a hit-dice mark or
parenthetical, a minus sign, spacing and case, a comma in a damage list read as
a slash, and a morale printed as two figures read as its first. A figure one
side did not read is a difference. A label two rows both match, and a row that
prints no single profile, are left made. A match is registered as a hash-keyed
pair for `le` in `creatureReplacement.json`, like the 41 before it.

The first run read 355 stat lines: 44 bound by a registered pair, 80 by name, 231
made in 224 label groups. Of those, 199 groups had a candidate row and were
compared; 5 groups, 5 stat lines, matched and are paired (10 keys, 5 rows, so
the register holds 91 keys over 44 rows); 194 groups, 201 stat lines, were
compared and did not; 25 groups had no candidate. The run after the pairs reads
49 bound by a pair and 226 made.

**Rejected:** matching a line whose attack or damage did not read, since an
empty figure agreeing with an empty figure is no agreement; a rule that lets a
variant match where it agrees at some occurrences of its label and not at
every one.

*Cost:* 226 of 355 stat lines are still made. Few rank-and-file lines match,
because L&E prints a figure that differs from the MM row's: a damage, a
weapon, a morale or a save. Near misses
stay made: a printed weapon's damage against the row's "by weapon", a label
whose occurrences disagree, a row whose attack text did not read, and the
rows that print a regular and a veteran profile. A paired line's creature is
the library's actor, so each such lair's printed residents bind to its monster;
the lair still rolls (the owner, "Yes, roll anyway", same day). The morale
rule reads only the first of two printed figures; the second goes unchecked.
